## 一、先定调：评委应记住的一句话

**不是又一个会报错的审校软件，而是编辑自己能配置的书稿处理工作台。**

编辑要做的事始终是：在有限时间里，于稿件的前后关系中发现疑点，借助工具书和参考资料查证，并完成修改。市面常见工具把这件事收成“一键检出 → 侧栏看标签 → 逐条采纳”。本扩展把这件事拆开交给编辑：

> PDF / Word → Markdown → 按稿件需要切分 → 按需要拼合（题与答、词典、维基、权威课文）→ 大模型按编辑规定的提示词修改 → 在全文差异对照里审核 → 生成勘误表

差异不在“也接了大模型”，而在三处：

1. **审得过来**：原稿删除、终稿插入成对着色，沿文脉看改动，而不是在侧栏标签和正文高亮之间来回跳。
2. **语境由编辑组织**：切分粒度、题目与答案是否拼在一起、参考资料放什么，都由编辑决定，不是厂商预设的错误类型菜单。
3. **工具长在真实稿件上**：作者本人是编辑，功能来自日常编校，而不是通用校对产品的功能清单。

建议赛道：**出版转型创新应用 → 出版流程智能化（编审校）**。  
作品形态：**已落地的产品案例**，不要写成尚待建设的方案。教育教学单元（智慧教材、智能教学助手）容易把评委带向课堂，不建议作为主赛道。

## 三、调研结论：目前审校工作卡在哪里

写申报书时用这些材料作对照，不堆厂商广告语。数字凡出自厂商自述（如“十万字三分钟”“准确率 80%–90%”），正文里标明“厂商宣传口径”，不拿来当本扩展的对比基准。

### 3.1 编辑实际要完成的事

工作坊方案第一节已经写准，申报书沿用并收紧：

- 低级错误（错字、标点、异形词）耗目力，时间紧就漏。
- 真正费劲的是长语境：前后表述不一致、专名写法不同、题与答对不上、引文与原文有出入。这些不是“再仔细一点”就能稳定发现的。
- 教参、练习册、注释类图书还要把课文、答案、词典、权威版本对到同一处。
- 三审三校不能减。工具的位置是辅助，不是替代。

2025 年 7 月《中国出版传媒商报》（中国作家网转载，《编辑使用 AI 编校工具实感体验》）里，一线编辑把痛点说得更具体：

- 科技社编辑：作者文字功底弱时，错字、搭配、语序、指代问题叠在一起，校对容易漏；早期粗用 AI 的感受是“用了不如不用，还不如自己审快”。
- 文学编辑：方正舆情“一击即中”，黑马“全年开花”，要在一大片红、粉标注里甄别；为了质量，同一部稿还要再过蜜度。**除人工审校外，稿件要分别过三遍软件**，编加已经很满时这几乎是奢侈。
- 古籍、学术编辑：引文被模型按文意改字（“詈”改“骂”、“叶”改“页”）是错的；知识性误改（人名张冠李戴）必须推翻。判断对错仍靠编辑。古籍是当前 AI 审校的短板。
- 另一位编辑指出：越是拼凑、无新意的稿，AI 越准；越是有学术空白、互联网检索不到的内容，AI 越帮不上。申报书不要承诺“学术硬核也能自动查实”。

英文编辑业讨论的是同一件事的另一面（Jane Friedman，2024；EditBook 等）：模型有时能改对，但**审这些建议本身极耗时间**；若结果不是可逐处看见、可拒绝的修订，编辑无法对作者负责。可见“查得出”之后，“审得过来”才是产品差异。

### 3.2 市面常见做法（三层，不要混成一个“传统软件”）

**第一层：规则型审校（黑马、方正字词与体例规则，及接入 WPS / Word 的插件）**

- 界面：文档内高亮，右侧列出错误类型和修改建议，逐条采纳、忽略或替换。黑马宣传语即“界面右侧出现侧边栏，逐个点击即可订正”。
- 擅长：错别字、敏感词、领导人排序、部分逻辑和格式。方正在章节编号、图表序号、引文落空、舆情上更强。
- 短板（行业文章与编辑自述，不是本扩展的自我评价）：长上下文和复杂逻辑弱；古籍、公式误报高；黑马标注过密，真错埋在误报里。编辑的时间花在“甄别标签”，不是“读改后的句子”。

**第二层：商业 AI 审校（方正已接大模型、蜜度校对通、武汉数传、中南智校、WPS AI 等）**

- 能力已明显超过纯规则：病句、专名、部分知识性差错、一致性。蜜度出版/期刊版甚至提供审校报告、勘误表，期刊形态还用“批注 + 修订痕迹”。
- 主界面仍是**错误列表**：右侧按全部 / 严重 / 一般 / 疑似分类，高亮定位，替换或忽略（校对通公开使用说明，2026-04）。
- 知识库、词库由厂商提供，编辑不能把“这一课的权威课文 + 这一题的答案 + 这一条词典”按自己的切分单元拼进同一次请求。
- 结果是编辑同时买多套、稿子过多遍，各补一块，流程仍是碎片的。

**第三层：把稿子贴进通用对话模型**

- 能改长句、能润色，但没有书稿流程：不能稳定切分十万字、不能把题与答对齐后批量提交、没有与原稿对齐的差异、不能累积勘误，也不能把个人正误表做成可重复的检查。编辑自己当胶水。

### 3.3 因此，对比时要打的是哪一仗

不要写“别人不能发现错别字，我们能”。2026 年这已经不成立。

要写的是：

| 编辑的真实动作 | 常见软件停在哪里 | 本扩展接着做了什么 |
|----------------|------------------|--------------------|
| 读一遍，判断改后的句子还通不通 | 读“错误类型 + 建议说明”，视线在正文和侧栏之间跳 | 全文 diff：删除与插入成对着色，沿文脉只看变红变绿处 |
| 题与答、正文与注释要在同一视野里 | 软件按厂商错误类型扫全文，编辑仍来回翻页 | 自行切分、自行拼合后再交给模型 |
| 古诗解释、专名、引文要查工具书 | 厂商知识库或模型记忆，依据不可替换、不可核对 | 编辑准备 reference，或由检索写入词典、文献、维基后再校 |
| 同一类问题全书统一改 | 侧栏逐条点 | 编辑器多光标、查找替换、正则；确认后的体例可进入编辑记忆或自制替换表 |
| 留下可复查的过程 | 采纳后原文被改掉，或只剩一份错误列表 | 原稿保留；diff、勘误表、git 提交都在 |
| 这部稿的特殊问题（注音、古籍用字、某套体例） | 等厂商排期 | 编辑自己写提示词和检查表，下一本书还能用 |

审核效率要写成机制，不要只写“高效得多”：

- 侧栏标签式：每条先读分类和解释，再回到正文看高亮，误报与真错在同一列表里；看到的是“建议替换某词”，不容易一眼判断改完后整句是否成立。黑马“全年开花”就是这种负担的行业说法。
- 全文 diff：模型交出的是改后文本，界面把原稿（删除）和终稿（插入）对齐。编辑按阅读顺序走，未改之处可跳过，改动处删除和插入同时可见。判断的是“这句改完对不对”，而不是“这条标签信不信”。
- 条目式输出是补充：只列出需改句、可按置信度筛选，但落到 diff 上核对，避免退回纯侧栏。

VS Code 生态单独写短段即可，避免变成软件说明书：并排/上下对照、多光标、多重选择、正则、Git。这些不是附赠功能，而是编辑在审核和统一体例时每天用的手。商业审校插件嵌在 Word 里，改稿手感止于“采纳/忽略”。

## 四、申报书建议结构

工作坊方案偏完整技术说明。申报书改成**产品案例**：少写 token、JSON 字段名，多写编辑动作。下面八节可直接当提纲；若官网表单更短，则 1–4 节为必写，5–7 节压缩，8 节放支撑材料。

### 0. 基本信息（表单，不进长文）

- 作品名称建议：`AI Proofreader：面向图书编辑的可配置审校工作台`（或更短：`图书编辑的 AI 审校工作台`）。避免只叫“智能校对系统”，和方正、蜜度撞车。
- 类别：出版转型创新应用 / 出版流程智能化。
- 关键词：图书编校、人机协同、差异对照、语境拼合、编辑定制。
- 一句话简介：用上面“先定调”的三句话，控制在 80 字内再写一版，看表单字数再取舍。

### 1. 编辑要完成什么（约 600–800 字）

从工作坊方案“业务痛点”改写，删掉软件名。先写人，再写工具不够。

写清四件事：通读找硬伤、长语境对照、工具书查证、把修改落到纸稿或电子稿并留下勘误。点明教参、练习册、注释类是本社常见稿，不是边缘场景。

收束句：瓶颈已经从“有没有软件查字”变成“查出来的东西审不审得过来，以及这部稿的语境能不能自己组织”。

### 2. 常见审校停在哪里（约 800–1000 字）

用第三节的三层，各用一小段。必须引用编辑自述（黑马全年开花、一稿过三遍软件、早期 AI 用了不如不用），让对比有出处，而不是贬低竞品。

诚实边界写在这里，后面就不必反复道歉：

- 政治表述、领导人排序、舆情，方正等专用工具仍然更合适，本扩展不替代。
- 商业 AI 已能改病句、查部分专名；本扩展不声称“只有我们懂语义”。
- 引文原文、古籍版本、模型没见过的学术材料，仍须编辑查证。胡宝亮所举“改引文、改错人”三类，声明本流程同样会遇到，所以审核界面必须让编辑一眼看见改了什么。

### 3. 本扩展怎样帮编辑做完（核心，约 1200–1500 字）

按编辑的一天来写，不要按命令清单写。一条主路径：

1. 来稿多为 Word，排版端常为活字 PDF。扩展内转为 Markdown（Windows 下 PDF 转文本已内置，不另装）。
2. 按目的切分：查字词和病句宜短（经验上约六百至八百字）；查前后一致宜按章，或给短段配上章节语境。
3. 需要时拼合：练习题与答案拼进同一段；古诗解释旁放入权威注释；专名旁放入词典条目。参考可来自编辑备好的文件，也可由检索去查本地词典、工作区文献、维基百科，编辑勾选后再并入。
4. 选用或自写提示词：硬伤、对应关系、表述、知识核查、拼音等可分轮做。同一本书多轮扫描，因为单轮又快又便宜（具体数字等测试后填）。
5. 在 diff 里审：深红删除、深绿插入。确认的修改由编辑誊到纸稿或写回。另可出勘误表、错词表。
6. 边读边改时不必走整书流程：选中一段即校。体例类修改可带编辑记忆，避免每段重复说明。

配一张总流程图（工作坊方案已有，申报书留一张即可）。命令名、面板四块不要展开。

### 4. 和常见审校的差异（评委最该记住的一节，约 1000 字）

只保留三个优势，每个都回答“所以编辑少做了什么”：

**优势一：审核看全文改动，不看侧栏说明书。**  
写机制（见 3.3）。配一张 diff 截图（后补），对比句用“常见侧栏：错误类型 + 建议 + 替换/忽略”。不要写“所有商业软件都没有修订痕迹”——蜜度期刊版已有批注和修订。差异要落在：本扩展的主结果是**整段改后文本与原稿的对齐对照**，编辑按读书的方式审，而不是按错误工单审。

**优势二：流程可按这部稿重排。**  
PDF → Markdown → 自定切分 → 自定拼合 → 大模型 → diff → 勘误表。举两个已在工作坊方案里写过的例子即可：练习册题答拼合后做“对应关系核对”；文言引文先检索词典和文献再做“知识核查”。强调编辑掌握切分、材料和提示词，模型不黑盒到底。

**优势三：长在编辑手里的编辑器，而不是另一套审校网站。**  
多光标与多重选择用于全书统一改法；Git 用于留下每一轮校对前的稿；正则、字词检查表、标题序号、重文、引文核对是日常碰到问题后补上的，不是演示功能。作者本人是编辑，在处理本社书稿中持续改软件。这一条同时回答“为什么可信”：需求来自岗位，不是来自产品经理访谈。

实用工具不列全表。正文点名 4–6 个能说明“从稿件里长出来”的即可，例如：方正带圈序号、题与答案标题对齐、半角标点、自制正误表、引文相似度核对、勘误表。其余放附录或支撑材料，避免像 README。

### 5. 用在哪些书上（3 个场景，各 150 字）

从工作坊方案压缩，每个场景固定四句：稿件长什么样、过去编辑怎么翻、现在哪一步交给工具、编辑仍亲自做什么。

1. 一般书稿：整书切分，批量预扫，diff 审硬伤与表述。
2. 练习册 / 教参：题与答或课文与解读拼合后核对对应关系。
3. 文言、学术、注释：参考资料准备好再校，编辑拿着依据查证，而不是对着一条无出处的“建议”。

位置声明用工作坊方案原意：**辅助三审三校，不替代法定程序，不自动写回定稿**。建议查证后誊录纸稿；除非编辑对电子稿有把握。

### 6. 已经怎样用、效果待填（占位）

已可写、不必等测试的事实（提交前与你核对一遍）：

- 作者为语文社编辑，自 2023 年底 DeepSeek 可用后按本人编校需要开发，开源。
- 已用于本人书稿，并有同事安装使用（工作坊方案写“约百种”“十多位编辑”——申报前改成你愿意公开的口径）。
- 不自建服务器，编辑自备 API 密钥即可。

测试后补的表格（现在不要编数字）：

| 项目 | 待填 | 备注 |
|------|------|------|
| 样本量 | 种 / 万字 | 注明文体：教辅、一般读物、文言等 |
| 处理时间 | 分钟 / 十万字 | 含不含切分与审核；审核时间单独列，避免把“模型跑完”说成“书校完” |
| API 费用 | 元 / 十万字 | 注明模型 |
| 审核方式对比 | 可选 | 若来得及：同一片段，侧栏式结果 vs diff，记录编辑确认一条所需操作。没有对照实验就不要写“效率提升 X 倍” |
| 正确率 | 慎用 | 若测，分开写：硬伤召回、误改率、编辑采纳率。不要给一个总准确率 |

没有对照实验时，效果节只写：模型预扫把“第一轮找疑点”从通读压缩到分钟级；编辑时间改花在查证 diff 标出的改动上。这是机制判断，不是测试数字。

### 7. 风险与边界（约 400 字，主动写，增加可信度）

- 幻觉、过度修改、漏检都会发生，必须人工审核。
- 切分不当会漏掉跨段问题，所以短段与长语境要结合，不能只宣传一种切法。
- 知识核查、编辑记忆更费 token，按需用。

- 不替代政治导向与重大选题的专项审读。
